# 阶段 1 复盘：group-buy-common

## 1. 本阶段完成了什么

本阶段完成了 `group-buy-common` 公共基础工程的最小建设。

当前只保留一个子模块：

```text
group-buy-common/
  group-buy-common-types/
```

`group-buy-common-types` 当前沉淀了：

- `Constants`
- `ResponseCode`
- `AppException`
- `Response<T>`

该模块已经完成构建验收，可以作为 jar 被后续业务服务依赖。

## 2. 原来有什么问题

如果每个微服务都各自复制一份 `Response<T>`、响应码、基础异常，会带来几个问题：

- 服务间响应结构不统一
- 基础异常语义不统一
- 后续 API 契约容易重复定义
- common 容易被误用成业务公共包

所以在正式拆 tag-service 前，先把稳定公共类型收口。

## 3. 我们为什么这样设计

`group-buy-common` 不是微服务，不启动，不注册 Nacos，也没有端口。

它只负责沉淀跨服务稳定复用的基础类型。业务模型、业务 DTO、数据库 PO、框架配置都不能放进 common。

这样做的核心目的是：

- 保持基础契约统一
- 避免业务模型共享导致服务边界变脏
- 避免 common 变成公共垃圾桶

## 4. 涉及哪些技术点

- Maven 聚合工程
- jar 模块设计
- 公共响应模型
- 业务异常封装
- 微服务公共依赖边界控制

## 5. 企业级体现在哪里

企业项目里的 common 模块必须克制。

本阶段没有把 Tag、Activity、Trade 等业务模型放进 common，也没有引入 Spring Boot、MyBatis、Redis、Dubbo、Nacos、Lombok 等框架依赖。

这说明 common 的定位是“稳定基础类型库”，不是“所有服务都能用的杂物间”。

## 6. 面试官可能怎么问

面试官可能会问：

- 为什么要单独抽 common 模块？
- common 里应该放什么，不应该放什么？
- 为什么不把业务 DTO 或领域模型放进 common？
- 如果 common 变大了会有什么风险？

## 7. 我应该怎么回答

可以这样回答：

```text
我在微服务拆分前先做了一个最小 common 工程，但没有把它做成大而全的公共包。

当前 common-types 只放跨服务稳定复用的基础类型，比如统一响应、响应码、基础异常和常量。业务 DTO、领域模型、数据库 PO、框架配置都不放进去。

这样可以保证服务之间基础契约统一，同时避免业务模型共享导致服务边界被破坏。
```

## 8. 当前还遗留什么风险

- 后续如果随意往 common 加工具类，仍然可能退化成公共垃圾桶。
- 如果响应模型过早固定，后续接口分页、错误详情、链路追踪字段可能需要谨慎扩展。
- common 模块版本升级后，需要关注下游服务兼容性。
